# S3: OS keychain through `@napi-rs/keyring`

Status: **measured on Windows and Linux (containers). macOS not available, so the macOS answer comes from docs and evidence and is marked untested.** Packaging answer: firm. Fallback design: firm for Windows and Linux. Two findings change the plan. First, on Linux the library's default store falls back to the in-memory kernel keyring without saying so. Second, a stuck D-Bus can block the calling thread, and no in-process timeout can stop that.

Reproduce the Windows measurement with one command: `cd docs/spikes/s3-keychain && npm ci && npm run bench:win`. That builds `dist/cli.js` with tsup and runs `bench-windows.mjs`: 20 fresh processes, sync and async, a warm loop, then it deletes the dummy entry and checks the delete. The output quoted below is in `bench-output-windows.txt`. Linux scenarios are in `linux/`; their commands are in §3. Environment: Windows 11, Node 22.23.3, npm 11.21.0, `@napi-rs/keyring` 2.1.1 (exact pin, published 2026-10-10, with npm provenance), tsup 9.0.0, esbuild 0.28.2, Docker 27.1.1 (WSL2 kernel 6.18). Other agents were using the machine during the runs, so the Windows p95 figures are noisy (see §2).

## Answer

`@napi-rs/keyring` **cannot go into a single-file bundle**, and neither can any other `.node` addon. Both tsup and esbuild refuse to build with it inlined. The only working "bundled" form is one JS file plus one `.node` file next to it. **Recommended packaging (option a):** tsup bundles every pure-JS dependency into one `dist/cli.js`. That file is identical on every platform. `@napi-rs/keyring` stays external and is declared in `optionalDependencies`. npm then installs only the host's prebuilt binary (0.5–3.2 MB, no install scripts, no node-gyp). Tested: `npm pack` → global install into a temp prefix and `npx --package <tgz>` on Windows, plus global installs in `node:22-bookworm-slim` (glibc binary) and `node:22-alpine` (musl binary). set, get and delete all work. A missing binary throws a catchable error at `import()`.

**Fallback design:**
- **Probe once, record the result.** `init` and `session-start` run a probe in a child process with a hard timeout. The probe does a set, get and delete. The result (`keychain` or `file`) goes into a non-secret `~/.prosegate/state.json`.
- **turn-end only reads the recorded backend.** A `file` backend never loads the addon.
- **Linux store is pinned to `secret-service`.** The default auto-selection falls back to the kernel keyutils store without saying so. That store is not persistent, and in one test it made a stored key look absent.
- **Linux and macOS read the keychain in a child process with about a 1 s timeout.** A stuck D-Bus blocks the native call synchronously: about 2 s for a frozen daemon, unbounded for a socket that never finishes auth. In-process timers, `AsyncEntry`, worker threads and `process.exit()` all failed to bound it.
- **Windows reads in-process.** The read took 15 ms in-process and 1 ms for `getPassword`.
- **"0600" on Windows needs `icacls`.** `fs.chmod(…, 0o600)` does not change the ACL.

Doc 05's "single-file build per platform" should become "a single platform-independent JS bundle plus a per-platform prebuilt keyring binary". The exact replacement text is at the end of this note.

## 1. Packaging

### 1.1 What happens when you try to inline the addon

| Attempt | Command | Result |
| --- | --- | --- |
| tsup, everything inlined | `npm run build:inline` (`noExternal: [/.*/]`) | **Build fails, 26 errors.** tsup's built-in `native-node-modules` plugin tries to resolve every `require('./keyring.<triple>.node')` in the napi-rs loader and fails on each one, including the installed one |
| tsup + `loader: { '.node': 'copy' }` | `npm run build:inline-copy` | **Same 26 errors.** tsup's plugin runs before the loader |
| plain esbuild | `esbuild src/cli.ts --bundle --platform=node` | **Fails:** `No loader is configured for ".node" files: …/keyring.win32-x64-msvc.node` |
| plain esbuild + copy loader | `npm run build:esbuild-copy` | **Builds and runs:** `cli.js` 35.8 KB plus `keyring.win32-x64-msvc-5LLYHZAX.node` 1.8 MB. Roundtrip passed when both were copied to an empty directory. Only the build host's binary is included; the other platforms' requires are left unresolved inside try/catch |

So no form gives one file. The closest is "one JS file plus one sidecar `.node` per platform". That gives nothing over (a): you still ship two files, and you have to fetch every platform's binary at build time.

### 1.2 Option (a): bundled JS, keyring external, `optionalDependencies`. **Recommended**

Package: `pkg/package.json` (`bin` → `dist/cli.js`, `files: ["dist"]`, `optionalDependencies: {"@napi-rs/keyring": "2.1.1"}`). Build with `npm run pack`, which writes `prosegate-spike-0.0.1.tgz` (2.0 KB, 2 files). `dist/cli.js` is 4.6 KB with the keyring external.

- `npm i -g prosegate-spike-0.0.1.tgz --prefix <temp dir outside the spike tree>` → `added 3 packages`. The only `.node` installed is `node_modules/prosegate-spike/node_modules/@napi-rs/keyring-win32-x64-msvc/keyring.win32-x64-msvc.node` (2.0 MB total). `prosegate-spike set|get|delete|getafterdelete` → ok / `got.equalsDummy: true` / `deleted: true` / `got: null`.
- `npx --yes --package <tgz> -- prosegate-spike get` → ran correctly from the npx cache. A quirk: `npx --yes C:/…/prosegate-spike-0.0.1.tgz get` from Git Bash exited 0 with no output and never ran the bin. That spec form doesn't matter for registry installs (`npx prosegate init`), but don't use it in docs.
- In Docker: `node:22-bookworm-slim` installed only `keyring-linux-x64-gnu`, and `node:22-alpine` only `keyring-linux-x64-musl`. Both ran. The glibc binary links only libc, libdl, librt, libpthread and libgcc_s (`ldd`), not libdbus. So a slim image with no D-Bus packages still loads it.
- Missing binary (I deleted `@napi-rs/keyring-win32-x64-msvc`): `import()` throws `Cannot find native binding. npm has a bug related to optional dependencies (…)`. With `@napi-rs/keyring` removed entirely it throws `ERR_MODULE_NOT_FOUND`. Both can be caught, and both should route to the file store.
- No package in the set has install scripts, so npm 11's install-script approval doesn't affect it. `@napi-rs/keyring@2.1.1` has SLSA provenance. Per-platform sizes (unpacked): win32-x64 1.9 MB, win32-arm64 1.7 MB, darwin-arm64 0.5 MB, darwin-x64 0.5 MB, linux-x64-gnu 3.2 MB, linux-x64-musl 3.2 MB, linux-arm64-gnu 2.8 MB.
- Test confound, noted for honesty: my first global-prefix test sat inside the spike directory. Node module resolution then walked up to the spike's own `node_modules`, so a "removed binary" still loaded. I redid the test with a prefix outside the tree. The results above come from that second run.

### 1.3 Option (b): Node SEA (one true binary per platform). **Works, not recommended**

`npm run build:sea` bundles with `@napi-rs/keyring` aliased to `src/keyring-sea.ts`. That shim embeds the `.node` as a SEA asset, writes it once to `~/.prosegate-spike/native/keyring-<sha256-16>.node`, and loads it with `process.dlopen`. Then it runs `node --experimental-sea-config` and `postject`. Result on Windows: set/get/delete pass. Cold `get` wall p50 64.9 / p95 72.3 ms, in-process 9.3 / 11.2 ms (`seabench.mjs`). Costs:
- an **87 MB** executable per platform;
- postject prints `warning: The signature seems corrupted!`, so every platform binary has to be re-signed (Authenticode; macOS `codesign`, which arm64 requires, plus notarization if the binary is downloaded);
- executable code is written into the user's home directory at runtime, which needs a hash check before every `dlopen`;
- it does not fit the `npx prosegate init` install.

Bun's `--compile` can embed `.node` files directly. I did not test it, and it changes the runtime.

### 1.4 Option (c): no native dependency, call OS tools. **Not recommended**

Windows test (`node shellout-win.mjs`): `powershell.exe` plus the WinRT `PasswordVault`, secret passed over stdin. set took 975 ms. **get p50 420 / p95 454 ms** (n=10), against about 1 ms for `getPassword` in the addon. delete took 527 ms. The entry was absent afterwards. On a fresh-process turn-end that is about 400 ms per turn, and PowerShell may be restricted (constrained language mode, AppLocker) on managed machines. Assessed, not tested:
- macOS `security add-generic-password -w <pw>` takes the secret **on argv**, where `ps` can see it. Items it writes trust `/usr/bin/security`, so any process that can run `security` reads them without a prompt.
- Linux `secret-tool store` does read the secret from stdin. But it needs `libsecret-tools`, which slim and server images don't include, and it hits the same D-Bus failures.

### 3.2 Hang guard: what actually bounds a blocked call

`linux/guard-test.cjs`. Modes: a worker thread with `process.exit()`, a worker with `process.reallyExit()`, a worker with `process.kill(process.pid,'SIGKILL')`, and a child process that is killed on timeout. Limit 1,500 ms each time.

| Mode | Stalled socket (`linux/out-hang-guard.txt`) | Frozen daemon, §3.3 J |
| --- | --- | --- |
| `--async --timeout` in the main thread | not tested (E above: >40 s) | timer fired only at 2,014 ms, after the constructor returned |

## 4. Fallback trigger and decision caching

**Backends:** `keychain` means Windows Credential Manager, the macOS login keychain, or the Linux Secret Service (always constructed with `{ linux: { store: 'secret-service' } }`; never use the default auto-selection or keyutils). `file` means `~/.prosegate/keys.json`.

**When it is decided:** `prosegate init` always decides. `session-start` re-decides when any of these holds: `state.json` is missing, `platform`/`arch`/libc or the keyring version changed since it was recorded, `reprobe: true` was set by a failed turn-end read, or the record is older than 7 days. turn-end never probes.

**Probe:** runs in a child `node` process. The parent `SIGKILL`s it after 1,500 ms, which is enough for the observed 2 s D-Bus timeout to count as a failure.
1. `PROSEGATE_KEY_STORE=file` → `file` (reason `forced`). `PROSEGATE_KEY_STORE=keychain` → probe, and fail loudly instead of falling back.
2. `await import('@napi-rs/keyring')` throws (`Cannot find native binding…`, `ERR_MODULE_NOT_FOUND`, a dlopen or Gatekeeper error) → `file`, reason `native_unavailable`.
3. Linux pre-check, an optimisation only: `DBUS_SESSION_BUS_ADDRESS` is unset and `$XDG_RUNTIME_DIR/bus` doesn't exist → `file`, reason `no_session_bus`, without loading the addon.
4. Construct an `Entry` for service `prosegate`, account `probe`. `setPassword` 32 random hex characters (not a real key), `getPassword` and compare, then `deletePassword`. Any throw, a mismatch, or the timeout → `file`, reason `probe_failed:<category>`. Do **not** branch on `err.code`: every failure observed was `GenericFailure`. For logs only, set `category` from the message prefix: `Platform failure` (no bus, connect failure, no reply), `Couldn't access platform storage` (no default collection, locked), `timeout`, `other`. Never log the raw message, because the load error's `cause` chain contains home-directory paths.
5. Otherwise → `keychain`.

`CI` is **not** a trigger. On a Linux runner with no session bus the probe fails in under about 50 ms. Windows and macOS runners have a working store. Forcing `file` because of `CI` would put keys on disk for no reason.

**Recorded state** (`~/.prosegate/state.json`, no secrets): `{"keyStore":{"backend":"keychain","reason":null,"probedAt":"…","platform":"linux-x64-gnu","keyring":"2.1.1","fileNoticeShownAt":null,"reprobe":false}}`. The one-time notice prints when `backend` first becomes `file`, and `fileNoticeShownAt` is set then.

**turn-end read:**
- `file`: read the file. Never import the addon.
- `keychain` on Windows: in-process sync `Entry.getPassword()` (15 ms in-process, measured).
- `keychain` on Linux and macOS: the read runs in a child process with a 1,000 ms limit, and the secret comes back over the stdout pipe (never argv or env). Start the child when turn-end begins so it runs in parallel with the rules engine. The extra cost is one node spawn, about 27 ms on Linux, mostly hidden behind S4's cold-start work.
- On timeout or error: rules-only, `stats.reviewer: null`, the once-per-session missing-key notice, and `reprobe: true`. **A turn-end failure never changes the backend.** A locked keychain is temporary, and moving keys to disk on a hiccup would weaken the threat model.

**Migration:** when a probe changes `file` → `keychain`, write the keys to the keychain, read them back, then delete the file. When it changes `keychain` → `file`, the keys can't be read anyway. Re-run device auth (`init`), and the reviewer key is vended again at the next session start.

**File store:**
- `~/.prosegate/` is created with mode 0700. Write `keys.json` to a temp file opened with `fs.openSync(tmp, 'wx', 0o600)`, then fsync and rename. Keep it separate from every config file so a config dump can never include it.
- POSIX: on read, `fstat`. Refuse to use the file, and warn, if `uid !== process.getuid()` or `(mode & 0o077) !== 0`, the same rule ssh applies to keys.
- **Windows: `fs.chmod` doesn't protect the file** (`chmod-win.mjs`, output in `chmod-output-windows.txt`). After `writeFileSync(…, {mode: 0o600})` and after `chmodSync(0o600)`, `stat` still reports `666` and the ACL is unchanged. `chmodSync(0o400)` only sets the read-only attribute (`R`). Use `icacls <file> /inheritance:r /grant:r *<user-SID>:F *S-1-5-18:F` at write time; it took 16–29 ms. Afterwards the ACL is `NT AUTHORITY\SYSTEM:(F)` plus the user `(F)`. Get the SID from `%SystemRoot%\System32\whoami.exe /user /fo csv /nh`. Use the full path, because Git Bash's `whoami` shadows it (this happened during the spike). Don't run icacls on the read path.
- **Why strip inherited ACEs on Windows:** under `%USERPROFILE%` the inherited ACL is already user, SYSTEM and Administrators only. In the relocated temp directory on this machine, though, a new file inherited two extra entries: a sandbox group with Modify, and an unresolved SID. Administrators can still take ownership whatever the ACL says. Disclose that rather than try to prevent it.

## 5. Logs, stderr, and whether errors echo the secret

- **Nothing on stderr from the addon** on any success or failure path. Windows checked with `2>file`, including `RUST_LOG=trace` (0 bytes). Linux checked with all output captured `2>&1`: only the spike's JSON appeared, plus messages from dbus-daemon and gnome-keyring themselves.
- **Error messages never contained the value.** I checked with a value that embeds the marker `prosegate-spike-dummy-not-a-secret`:
  - Windows `setPassword` with 7,000 characters → `Value of 'password encoded as UTF-16' is longer than the platform limit of 2560 chars`, both sync and async. The marker was absent.
  - Windows `getPassword` on stored bytes that aren't valid text (`badenc.cjs`) → a 32-character message, `Password data is not valid UTF-…`, with neither the text nor the byte list.
  - Every Linux error in §3 carries neither the value nor the service or account name. Linux accepted the 7,000-character value, so no set-error exists there to inspect.
- **What can leak:** dbus-daemon logs each service activation together with the **requesting command line** (`requested by ':1.0' (uid=0 pid=25 comm="node /usr/local/bin/prosegate-spike set")`). Never pass a key on argv. The cause chain of a load error includes absolute paths, which contain the username. Map errors to categories before they reach telemetry, in line with 07's "keys never in logs" and the bounded-strings rule.
- **Windows size limit:** 2,560 bytes of UTF-16, so 1,280 UTF-16 code units at most. OpenAI service-account keys and a 32-byte device key in hex or base64url fit easily. Add a unit test that rejects keys longer than 1,000 characters.

## 6. macOS (untested, best evidence)

- **Binaries:** `@napi-rs/keyring-darwin-arm64` (526 KB) and `-darwin-x64` (543 KB) are in `optionalDependencies`. No universal package is published; the loader only looks for a local `keyring.darwin-universal.node`.
- **Signing (upstream issue Brooooooklyn/keyring-node#149, opened 2026-10-11, open, no maintainer reply):** the macOS prebuilt binaries are ad-hoc signed only, with no Developer ID and no notarization. If the files carry a quarantine or provenance mark, because they came through a browser download or were installed by another app, Gatekeeper rejects them and `require` fails with `Cannot find native binding`. The issue reports that a plain `npm install` in a terminal works. `npx prosegate init` from a terminal is that case. Probe step 2 already routes a Gatekeeper failure to `file`. Option (b) would need Prosegate to sign and notarize its own binary.
- **Keychain access prompts:** for a legacy login-keychain item, the ACL trusts the **process executable that created it**, which is `node`, not the `.node` addon. Apple's documentation and developer threads say a prompt ("node wants to use your confidential information…") appears when the reading binary's code identity differs from the creator's. Two likely cases:
  - Homebrew's node, which is ad-hoc signed, so its identity changes with every upgrade;
  - switching between node versions with nvm or volta.
  
  Official nodejs.org builds are Developer-ID signed, so their designated requirement should stay stable across upgrades. **All of this is inference, untested.**
- **Consequences:** run the first probe from `init` in an interactive terminal, so the user sees the prompt once and can choose "Always Allow". On turn-end a prompt would block a background hook until someone answers it, which is why §4 puts macOS reads in a guarded child process. Over SSH with no GUI I expect a fast `errSecInteractionNotAllowed`, which is untested.

## 7. Cleanup

Every entry the spike created was deleted, and the deletes were checked:
- **Windows:** `node verify-cleanup.cjs`, which queries only the `prosegate-spike` service, returned `{"service":"prosegate-spike","remaining":0,"accounts":[]}`, `device-key present:false` and `badenc present:false`. I checked the verifier against a live entry first (`remaining:1`) so that a 0 means something. The PasswordVault resource `prosegate-spike-ps` reported 0 entries. No `~/.prosegate-spike*` directory exists; the SEA test extracted into the scratch directory.
- **Linux:** every container ran with `--rm`. Secret Service entries were deleted and checked with `getafterdelete → null`, and they lived in an in-memory collection of a daemon that is gone. One keyutils entry, from scenario D on the first run, was not deleted in-run (the script now deletes it). It was in that container's session/persistent keyring, a fresh container could not see it, and keyutils is in-memory only. I cannot read `/proc/keys` on the WSL2 kernel to prove it was freed, so that one is "not visible", not "verified deleted".
- No existing keychain entry was read or listed. Every lookup named a spike service.

## 8. What I'm unsure about, and what wasn't tested

- Everything on macOS (§6).
- Windows: access to Credential Manager from SSH, service or network logon sessions. CredWrite can fail with "logon session does not exist" there; the probe would catch it, but I didn't test it. Windows arm64 was not tested either.
- Linux: a real persistent login keyring that is locked and prompts through gcr; KWallet; KeePassXC. The 2 s reply timeout is what I observed from `dbus-secret-service`; I did not read the source.
- The unbounded hang needs a socket that accepts connections but never finishes D-Bus auth. That is pathological, but it is reachable (a wedged dbus-daemon), and it is why the child-process guard exists.
- Windows latency figures were taken on a shared, noisy machine. The p50s are stable across runs; treat the p95s as upper bounds.

## Proposed correction for doc 05 "Packaging"

Replace the paragraph with:

> `prosegate` ships as an npm package containing one platform-independent JavaScript bundle (`dist/cli.js`, all pure-JS dependencies inlined by tsup) and one native dependency, `@napi-rs/keyring`, kept external to the bundle and declared in `optionalDependencies`; npm installs only the prebuilt keyring binary for the host platform, with no install scripts or compiler. A `.node` addon cannot be inlined into the bundle. If the binary is absent or fails to load, keys use the file store described in 07. The package is installed with `npx prosegate init --harness claude-code`, which writes the hook and MCP registrations, probes the key store once and records the result, and runs `session-start` once to confirm auth. The shim scripts are inside the package; a user never edits them.
