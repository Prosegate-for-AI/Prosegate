# S2 - OpenAI reviewer-key vending

Status: **script ready, awaiting run by the product owner.** Nothing here has been run against OpenAI. The script was exercised offline only (self-test, dry run, and a throwaway localhost mock of the endpoints). Docs and spec read 2026-10-17.

Run it: `docs/spikes/s2-openai-vending/README.md`. Output: `s2-report.json`.

## Answer so far

**Plan section 1 is out of date on the central point: OpenAI now has a per-project hard spend limit, settable through the Administration API.** `POST /v1/organization/projects/{project_id}/spend_limit` with `threshold_amount` (integer cents, minimum 1), `currency: "USD"`, `interval: "month"` creates or replaces it; `GET` reads it (404 when none); `DELETE` removes it. The response carries `enforcement.status` (`inactive` or `enforcing`). An organization-level twin exists at `/v1/organization/spend_limit`. The plan's "no endpoint" evidence is a community thread whose last reply is 2025-08-01; the endpoints were added to the public spec on 2026-07-23, after it.

What is still open, and what the script measures, is whether it **actually enforces, how late, and how far past the cap**. OpenAI's own guide says enforcement "is not instantaneous" and that "recorded spend can slightly exceed the configured amount". The provisional design is therefore belt and braces, not rate limits alone:

1. Per-user project with a **hard monthly cap** (the 07 default of USD 5 maps directly: cents, month).
2. **Project rate limits** (requests and tokens per minute, model allowlist) to bound how fast a stolen key can reach that cap and how expensive a token it can buy.
3. **Cost polling every 15 minutes plus revoke by deleting the service account**, as already written in 07, as the second line.

Worst-case exposure per key then has two parts, both computed by the script: the rate-limit-and-polling figure (the formula you specified) and a cap-plus-overshoot figure. The doc owner decides whether ADR-3 keeps the words "hard spend limit" (now truthful) and adds the caveat "enforced with lag; overshoot measured in S2".

Design consequences worth carrying into 06 section "Usage poller": the costs endpoint only has **daily buckets**, so a 15-minute poller that wants intra-day burn detection should read `usage/completions` at `1m` or `1h` buckets (tokens times a price table) and use `/costs` as the reconciling source. The script measures the lag of both so this can be decided on data. `api_key_ids` filters allow per-key rather than per-project accounting. `expires_in_seconds` on the service account gives a native key TTL for the 30-day rotation in 07.

## Could not verify

- Any **live behaviour**: response bodies beyond the spec's examples, the actual lag of costs and usage reporting, whether the spend limit blocks in seconds or minutes, whether SA deletion kills the key at once. These are exactly what the script measures.
- The **HTTP shape on `/v1/chat/completions`** when the project cap is hit, beyond guide B's "429 plus `project_spend_limit_exceeded`" (the script records status, `type`, `code`, message).
- Whether the spend-limit and model-permission endpoints are available to every sandbox org and admin key (403 is a documented response). The script records this per call.
- The **array query encoding** for `project_ids`: the spec does not state `project_ids[]=` versus repeated `project_ids=`. The script tries brackets, falls back to repeated on a 400, filters client-side by `project_id`, and records which worked and whether the filter was effective.
- Whether the costs endpoint reports **sub-cent** amounts; if it rounds, tiny calls will never appear and only the larger enforcement-test calls will.
- Whether `max_requests_per_1_day` and `batch_1_day_max_input_tokens` apply to the chosen model, whether project limits may exceed the org's own, and whether a service account's default key can call `GET /v1/models`. The script records accepted/rejected fields individually and read-back values.
- The **price table**: Source C was read through a summarising fetch tool, so treat the numbers as indicative. The script takes prices as flags and reports the blended price implied by the actual cost, so any mismatch shows up in `observed.reported_over_expected_ratio`.
- A forum report from May 2026 (seen only in a search-engine summary) of a project running past its cap while showing under budget. Unconfirmed; it is a reason to run the enforcement test and to keep polling-and-revoke as the second line.

## Provisional exposure formula

```
worst_case_exposure_per_key_usd
  = max_tokens_per_minute x price_per_token_usd
    x (polling_interval_min + cost_reporting_lag_min + revoke_latency_min)

price_per_token_usd = max(input_price, output_price) / 1e6   (a token limit does not constrain the mix)
polling_interval_min = 15 (06/07);  lag and revoke latency come from the run
```

Illustration only, with inputs that are **not measured**: at 10,000 tokens per minute on gpt-4o-mini (USD 0.60 per 1M output tokens) a minute at the limit costs USD 0.006, so the 15-minute polling term alone is USD 0.09, and every extra minute of reporting lag or revoke latency adds USD 0.006. A secondary figure, `exposure.with_hard_cap`, is `cap_usd + tokens_per_minute x price_per_token x enforcement_lag_min`, valid only if the enforcement test shows the cap holds. The tokens-per-minute value is a design choice (`--tpm`); the script's default of 10,000 is a placeholder, and the number in the admin doc must use the limit actually vended.

## Decisions for the doc owner once the report is back

- ADR-3 and 07 "Key handling": keep "hard spend limit" if `enforcement_blocked` is true and the overshoot is small; state the measured lag and the polling backstop. If it is false or the overshoot is large, rewrite as in plan section 2 item 2 and state the rate-limit-times-window figure instead.
- Vending order in 06: create project, set rate limits and model allowlist, set the hard cap, create the service account with `expires_in_seconds`, hand over the key. Add the cap and limits to the "cannot do" checks (the vend call must fail closed if any of them cannot be set).
- Poller: bucket choice (usage 1m/1h versus costs 1d) from the measured lags.
