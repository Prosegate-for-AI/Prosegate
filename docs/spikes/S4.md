# S4 — re2js budget for the `core` pack

Status: **measured; answer is conditional.** Plain transcription of 08 into `re2js` (word-bounded alternations, case-insensitive flag, one `Matcher` over the whole document) **misses the 50 ms budget**. The same patterns run through three engine-side changes (no `\b` inside RE2, per-paragraph matching, JS boundary check) come in at single-digit milliseconds warm with identical findings. The residual risk is **cold start** in a process-per-event hook, not the regex engine.

Rerun: `cd docs/spikes/s4-re2js && npm ci && node bench.mjs` (about 3 minutes; sections can be run alone: `node bench.mjs api|correct|unicode|bench|scale|cold`). The exact output of the run quoted below is in `s4-re2js/bench-output.txt`. Environment: Node 22.23.3, `re2js` 2.8.6 (exact pin; 2.8.7 appeared on npm while the spike was running, is younger than the workspace's 24 h `minimumReleaseAge`, and was not tested), Windows 11, i5-11400H, machine under ~60% background load from other processes during the runs (see "How far to trust the numbers").

## Answer

**Does the pack fit 50 ms p95 on 2,000 words with re2js? Not as the plan describes it; yes with restructuring.** The naive pipeline (08 phrase lists compiled to one `\b…\b`, `(?i)` alternation per rule, `Matcher.find()` over the whole text; plan §6.3) took **p50 51 ms / p95 59 ms / max 101 ms** warm for the full 23-rule pack on a 2,000-word document (43/58/64 ms on a dense-hit document); across six runs on this noisy machine its p95 ranged 45–85 ms. The regex part alone is 47 of those 51 ms. The restructured pipeline ("opt B": patterns without `\b`, lowercase copy of the text, `Matcher` per paragraph, boundaries verified in JS) took **p50 6.6 ms / p95 7.7 ms / max 8.0 ms** (dense: 6.9 / 9.6 / 13.1), with byte-identical findings on 1,541 rule×text comparisons; the native `RegExp` reference with the same JS scaffolding took 4.1 / 4.9 ms. So warm, re2js is within roughly 1.6–2.5× of native `RegExp` once structured properly, with 5–6× headroom against the budget. **Neither precompiled-program caching nor native `re2` is needed for the warm path:** `re2js` has no program serialization API at all, and compile is only 1–2 ms warm, so the lever is how patterns are used, not how they are compiled. The unresolved item is **cold start**: a fresh `node` process pays about **54 ms p50 / 86 ms p95** of engine work (17–20 ms pack compile plus 32 ms first run, all V8 and lazy-DFA warm-up) on top of about 17 ms module load, versus about 19 ms for the same pipeline on native `RegExp`. If the Stop hook is one `command` process per event (plan §1, hooks row), the 50 ms figure will not hold on a cold process with re2js; a warm process (MCP server, daemon) would. I did not measure native `re2` (not installed; installing a native addon was out of scope), so I cannot say whether it fixes cold start.

| "game‑changer" with U+2011, "cutting‐edge" with U+2010 | **0** | 1 |

**A curly apostrophe silently defeats every rule whose pattern contains `'`** (eleven phrases and two regexes), and curly quotes are common in model output. Recommended normalisation, applied once before matching: U+2018, U+2019, U+201A, U+201B, U+02BC, U+2032 → `'`; U+201C–U+201F → `"`; U+00A0, U+202F, U+2009, U+2007, U+2002, U+2003 → space; U+2010, U+2011 → `-`. Every mapping is one UTF-16 code unit to one code unit, so **offsets are unchanged** (the script asserts `length` equality) and the finding's `span.text` is sliced from the original string, which keeps the user's curly quote in what is displayed. Do not map U+2013/U+2014. Cost: 12–17 µs on 2,000 words. Not handled: zero-width characters and soft hyphen inside words (not 1:1; rare in model output).

`\b`, `\w` and `\s` are ASCII-only in re2js (and in native JS): `\w` does not match "é", `\s` does not match NBSP or U+2028, `\pL` does. Consequences: `\bve\b` matches inside "naïve"; `\bcaf\b` matches inside "café"; `\brobust\b` matches in "robustés" and "érobust"; and `core.triad.001` on "The naïve, simple, and robust option." matches "ve, simple, and robust", starting mid-word. ASCII `\b` can only produce extra boundaries, never miss one, so the fix is a post-check: after a match, reject it if the adjacent character is `\p{L}\p{N}_\p{M}` (implemented as `unicodeBoundaryOk`; costs nothing measurable). The restructured pipeline does this and thereby becomes Unicode-aware, which the in-regex `\b` cannot be.

Em/en dash: "robust—and", "—robust", "we delve—briefly", "seamless–robust" all match their phrase rules (dash is a non-word character, so `\b` holds on both sides); the sentence splitter correctly does not break at a dash; `\s+` in a multi-word phrase does not span a dash, as it should not. `hedge.005`: "It depends…" with U+2026 does **not** fire (`[.!]` only); 'He said "it depends."' and "It depends!!" do.

`(?i)` in re2js applies Unicode simple case folding: `(?i)k` matches U+212A (Kelvin sign) and `(?i)s` matches U+017F (long s). Harmless for this pack, but it means "case-insensitive" is not ASCII-only; the recommended pipeline lowercases ASCII only (A–Z → a–z, 1:1), which drops this and keeps offsets (`String.prototype.toLowerCase` can change length, e.g. U+0130, so do not use it).

## re2js API facts the engine depends on

- **Offsets are UTF-16 code units (JS string indices), not bytes or code points.** With three astral characters before the match, `indexOf` = 11, `Matcher.start()` = 11, code-point index would be 8; `text.slice(m.start(g), m.end(g))` round-trips. `exec()`/`matchAll()` results expose only `.index` and `.groups` (named), with **no group offsets** (`indices` absent), so use `Matcher`.
- **Group 1 offsets:** `m = re.matcher(text)`, `m.find()`, then `m.start(1)` / `m.end(1)`; `-1` if group 1 did not participate; `m.groupCount() === 0` if the pattern has no group. 04's "group 1 if present, else whole match" therefore needs the explicit `-1` fallback.
- **Global iteration:** `while (m.find()) {…}` is stateless per `Matcher` and continues after the previous match; `m.find(start)` resets and searches from `start` (used to resume after a rejected candidate). `re.matchAll(text)` is a stateless ES iterator. There is no `lastIndex`.
- **Case-insensitive:** `RE2JS.compile(p, RE2JS.CASE_INSENSITIVE)` or inline `(?i)`; both work.
- **Syntax rejected** (throws `RE2JSSyntaxException` at compile): backreferences, lookahead, lookbehind, atomic groups, possessive quantifiers, repeat counts above 1,000. **Every pattern in 08, once unescaped, compiles.** `(?P<n>…)` and `(?<n>…)` named groups are accepted.
- **`RE2JS.LOOKBEHINDS` is a non-standard opt-in flag** in 2.8.x that makes `(?<=…)` compile. The loader must never pass it, or packs stop being portable to Go/C++ RE2 and node-re2.
- **Matching strategy matters more than pattern length.** From the source (`executeEngine`): a search that needs capture offsets uses the BitState backtracker only when the input is no longer than `MAX_BACKTRACK_VECTOR / program size`, otherwise the Pike NFA; boolean `test()` uses the lazy DFA. The README says patterns with `\b` bail out of the DFA to the NFA. The measurements agree (`exp.mjs`, saved in `exp-output.txt`, all 17 patterns on the 12k-char document, p50): `test()` with `\b` 39.3 ms, without `\b` 2.1 ms (rows 2 and 3); `find()` loop over the whole text is slow with or without `\b` (53.8 ms with, 24.4 ms without plus lowercasing; rows 1, 5, 6) and fast on paragraph-sized chunks (3.1 ms without `\b`; row 9, but 57.3 ms with `\b`; row 8); `RE2Set` over all 17 patterns is 0.2 ms without `\b` and 46.1 ms with it (rows 10–12). So both changes are needed: removing `\b` unlocks the DFA, chunking unlocks BitState for the offset-producing pass.

## Recommendations

1. **Use the opt B pipeline in `packages/engine`** (all in `docs/spikes/s4-re2js/engine.mjs`, `buildPackOpt`, as a reference implementation, not production code):
   1. Normalise (1:1 mapping above), then make an ASCII-lowercased copy; compile patterns case-sensitively on the lowercase copy. Loader requirement: pack regexes must be written lowercase (all 08 ones are), or the loader lowercases literals.
   2. Strip a leading and trailing `\b` from each compiled pattern; after each candidate match verify the boundary in JS only where the match's edge character is a word character, using `[\p{L}\p{N}_\p{M}]`. On rejection resume with `m.find(start + 1)`.
   3. Run each part per prose chunk (a paragraph, or a group of sentences up to about 1,500 chars for long paragraphs) and add the chunk offset. plan §6.2's segmenter already splits prose at blank lines, so this is the same unit.
   4. Apply `position`, `max_doc_words` and sentence-scope filters as JS post-filters, memoised per sentence.
2. **Do not** use `RE2Set` as a gate (30 ms first-match cost cold, no warm gain at this size), do not rely on `NODE_COMPILE_CACHE`, and do not spend effort on "precompiled-program caching": there is no API for it and compile is 1–2 ms warm.
3. **Decide the process model before closing S4.** Per-event `command` hook: budget about 54 ms p50 / 86 ms p95 of cold engine work plus about 17 ms module load for this pack (about 19 ms engine work with native `RegExp`, so most of the gap is re2js-specific cold JIT and DFA setup). Options, none measured here: a long-lived process (the MCP server route noted in plan §1), a V8 startup snapshot (`node --build-snapshot`), measuring native `re2`, or relaxing the budget to "warm p95". Re-measure once the real bundle exists; tsup output will change module-load cost.
4. **Cap `similarity_to_prior`**: 3 ms at 2,000 words but 39 ms at 8,000 and 125 ms at 16,000. Either skip above about 6,000 words, compare only against sentences sharing a content word (inverted index), or bound the lookback window. Define the stop-word list in 04 (it changes the 08 hit example's outcome) and whether "min 6 words" applies to both sentences.
5. **Spec corrections for 08/04 (for the orchestrator; I did not edit 08):**
   - State regex flags per rule; default to case-insensitive (hedge.005 and vocab.002 hits fail without it).
   - Spans: replace capturing groups used for alternation with `(?:…)` and make the span explicit. As written, group 1 yields "The" (vocab.002), "effective" (vocab.004), "fast" (triad.001), "just" (triad.002), " and " or nothing (triad.003). hedge.002 yielding only the qualifier may be intended.
   - Replace triad.001's miss example with one that is a true miss (for example the digit case "It is fast, simple, and reliable on 3 runners.") or move the git/node/pnpm sentence out of `miss`; as written the eval harness would refuse to publish the rule.
   - structure.002: either change the metric so the 12-key list misses (count list items in prose-only sentences, or weight by words) or change the example; structure.003: give the miss ≥10 sentences.
   - hedge.001: split `note that` into its own rule or give `phrases` per-phrase positions.
   - Add the per-edge boundary rule to 04's `boundary: word` definition (word-character edges only).
   - Fix the rule count (23) and the 04 example id; add an exclusion for "rather than" to hedge.002 (engine-level `not_followed_by: [than]`, since RE2 has no lookahead) or drop `rather`.
   - Add loader lint: reject `\|` and `\\b` in patterns, and require each rule's `hit` examples to match and `miss` examples not to match at load.
6. Phrase patterns should use `\s+` between words (done in `phrasePattern`) so a line wrap inside "let me know if you have any questions" still matches.

## How far to trust the numbers

- **Machine noise.** Other processes (a disk indexer, other agent sessions) held the CPU at about 60% during the runs. Naive p95 varied 45–85 ms between runs, opt B 7.4–11 ms. The ranking of variants was stable in every run; absolute values are not. Rerun on a quiet machine before quoting a number in a milestone.
- **Synthetic corpus.** The 2,000-word document is generated from templates with injected hit sentences, not real model output. Real prose with more commas, quotes and capitals might shift costs by tens of percent; the pathological and dense cases suggest no cliff.
- **My engine is a stand-in.** The splitter is a simple hand-rolled one (it treats "a." as an initial, so single-letter sentences merge), the structure metrics are minimal, and the segmenter (code fences, tables, quotes) is absent. Nothing here exercises code-block removal, which would reduce text length and cost.
- **Not measured:** native `re2`; macOS or Linux; Node versions other than 22.23.3; a bundled single-file build; memory.
- The optimised and naive pipelines agree exactly on 08's examples, the supplementary probes and five generated documents (1,541 comparisons). They are not guaranteed to agree on adversarial text where in-regex `\b` would have found a different, later alternative after a rejected candidate (for example "butter" after a lazy `, but` in triad.002); the optimised pipeline resumes one character after the rejected start.
